2. Executive summary

What it does. AeroBase India gives an airport one shared, tenant-scoped system of record. The airport director, airline operations, pilots, security, ground staff, shop owners and passengers each sign in to a workspace shaped for their job, on top of one flight, gate, crew, baggage, booking and order dataset.

Who it is for. Airport operators (the tenant), the organisations that work inside an airport (airlines, concessions, security), and passengers. A platform owner role sees all airports.

Why it exists. A single delayed flight touches gates, baggage, security queues, crew, retail and passengers, and each party usually learns about it through a different tool at a different time. AeroBase puts them on one data model and enforces the rules on the server: for example a passenger cannot be boarded until check-in, bag drop and security screening are recorded, and the API answers 409 otherwise.

5.1 React 19

What it is
A component-based UI library that renders a tree of functions into DOM and re-renders only what changed.
Why chosen for this project
The product has about 128 page files across 30+ role and domain folders that share layout, tables, KPI cards and forms. Components give reuse without a framework-imposed structure, and lazy loading keeps each role's bundle small.
Alternatives considered
AlternativeProsConsWhy rejected
Vue 3Gentle learning curve, good reactivitySmaller hiring pool for the target team; fewer ready libraries for three.js integration I wantedReact was already the author's strongest stack
Svelte / SvelteKitSmall bundles, little boilerplateYounger ecosystem, fewer testing and chart librariesEcosystem depth mattered more than bundle size
AngularBatteries included, strict structureHeavy for a solo-built SPA, steeper setupToo much ceremony for the team size
Advantages gained
Large ecosystem (Recharts, TanStack Query, Testing Library), concurrent rendering, hooks for shared data logic (useBoard, useCollection).
How it works internally
State changes schedule a render. React builds a virtual tree, diffs it against the previous one in the reconciler, and commits only the minimal DOM mutations. Hooks store per-component state and effects in a linked list on the fiber.
How it is wired in this codebase
Entry frontend/src/main.tsx; shell and role routing in App.tsx (49 lazy() imports behind Suspense); shared UI in components/ui and components/layout.

5.2 TypeScript 6

What it is
A typed superset of JavaScript that is checked at build time and erased at runtime.
Why chosen for this project
Role names, API payloads and booking states are shared across many files; the compiler catches renames and missing cases before runtime. The build script runs tsc -b before bundling.
Alternatives considered
AlternativeProsConsWhy rejected
Plain JavaScript + JSDocNo build step for typesWeak refactor safety at this sizeRefactors across 100+ pages need compiler help
FlowGradual typingLittle ecosystem momentumTooling and community are in TypeScript
Advantages gained
Compile-time errors for contract drift, editor autocomplete, safer refactors.
How it works internally
tsc parses sources, builds a type graph, reports errors, and (with Vite) transpilation is done by esbuild/Rolldown which strips types without checking them.
How it is wired in this codebase
tsconfig.app.json, types in src/types; typed stores such as UserRole in store/authStore.ts.

5.5 TanStack Query 5

Why chosen for this project

Alternatives considered
AlternativeProsConsWhy rejected

6.1 C++17 with CMake

What it is
A compiled systems language and its build tool; the API is a single native executable.
Why chosen for this project
Low per-request latency and memory on small free-tier instances, and a single binary to ship in Docker. The project also serves as a systems-engineering portfolio piece (⚠ ASSUMPTION about motive).
Alternatives considered
AlternativeProsConsWhy rejected
Node.js / ExpressFast iteration, same language as frontendHigher memory per instance, GC pausesNative performance and footprint were preferred
Go (Gin/Fiber)Simple concurrency, fast buildsDifferent ecosystem than the author's chosen C++ stackNot rejected on technical grounds; a valid alternative
Java Spring BootMature enterprise stackJVM memory on free tierFootprint
Python FastAPIQuick to writeSlower, GILUsed only for the ML service
Advantages gained
Small runtime footprint, deterministic performance, compile-time type checking. Cost: long compile times (the Render build needed -j2 and GCC memory flags to fit free-tier RAM) and slower feature iteration.
How it works internally
CMake collects src/*.cpp and *.cc, links Drogon, libpqxx, hiredis, OpenSSL and libuuid, and emits one executable. The Dockerfile builds in an ubuntu:24.04 stage and copies the binary to a runtime stage.
How it is wired in this codebase
CMakeLists.txt (CMAKE_CXX_STANDARD 17), Dockerfile (multi-stage), src/main.cpp (entry).

6.2 Drogon

What it is
An asynchronous C++ HTTP and WebSocket framework built on an event-loop thread pool.
Why chosen for this project
Non-blocking I/O with controller auto-registration, pre-routing advice for central guards, and built-in WebSocket and HTTP client support.
Alternatives considered
AlternativeProsConsWhy rejected
Crow / Oat++LighterSmaller feature set, fewer examplesDrogon has filters, advice hooks, async client
Boost.BeastMaximum controlEverything hand-builtToo much plumbing
PistacheSimpleLess activeMaintenance risk
Advantages gained
Declarative routes (ADD_METHOD_TO), request filters, global advice for CORS and the route guard, native JSON via jsoncpp, threads_num: 8.
How it works internally
Each IO thread runs an epoll event loop. A request is parsed, passes pre-routing advice, is matched to a handler, and the handler answers through a callback. Blocking calls stall a loop, which is why DB connections are per-thread.
How it is wired in this codebase
src/controllers/* (about 60 controller sources), src/main.cpp (pre-routing advice: CORS then routeguard::check; post-handling advice adds CORS headers), src/config/config.json, src/middleware/*.

6.5 jwt-cpp and OpenSSL

What it is
A header-only JWT library and the cryptography toolkit.
Why chosen for this project
Stateless authentication carrying user_id, tenant_id, role, name, email, airport and org so that no database read is needed to authorise most requests. OpenSSL provides PBKDF2 for passwords.
Alternatives considered
AlternativeProsConsWhy rejected
Server sessions + RedisRevocableShared store required on every requestStateless preferred for free-tier hosting
OAuth / OIDC providerDelegated identityThird-party dependency and costNeeds to work self-contained
bcrypt/argon2Stronger against GPUs (argon2)Extra libraryPBKDF2-HMAC-SHA256 at 600,000 iterations follows OWASP guidance and uses OpenSSL already linked
Advantages gained
Tokens signed with HS256 and a configurable TTL (default 8 hours, clamped 60 s to 7 days). Passwords stored as pbkdf2$iterations$salt$hash with a random salt; legacy unsalted SHA-256 hashes still verify so old accounts work.
How it works internally
A JWT is base64url(header).base64url(payload).HMAC-SHA256. Verification recomputes the HMAC with the secret, compares, and checks exp.
How it is wired in this codebase
services/JwtService.cpp (hs256, JWT_TTL_SECONDS), services/PasswordService.h, services/AuthService.cpp (dummy-hash verification so unknown emails take equal time), services/LoginThrottle.h, external/jwt-cpp.

Why chosen for this project

Alternatives considered
AlternativeProsConsWhy rejected

7.5 Migration strategy

Plain numbered SQL files 001 to 045, written with IF NOT EXISTS and ON CONFLICT DO NOTHING so they can be re-run safely. scripts/bootstrap.py applies them in order on every container start (waiting for the database first), then loads reference data once, then optionally seeds demo data. CI has a migration-numbering check. Some early tables were redefined in later migrations (for example subscription tables appear in 009, 018 and 031, and migration 038 reconciles billing); this is schema debt, listed in section 16.

7.6 Scaling path

The k8s manifests in deploy/k8s include an HPA, Postgres and Redis. Login throttling is in-process, so with several replicas it should move to Redis (⚠ ASSUMPTION about the roadmap).

7.7 Backup and recovery

scripts/backup.sh exists in the repo for dumps. On Render's free Postgres the instance expires after 30 days (noted in render.yaml), so a permanent managed database such as Neon is recommended in docs/DEPLOY_RENDER_VERCEL.md. Because migrations and the bootstrap are idempotent, an empty database can be rebuilt to a working state, but user-created data needs a real backup. Restart safety was verified: restarting the container keeps data.

11.4 Build and release workflow

  1. Push to main (the project pushes directly to main, no pull requests).
  2. Pre-commit hook and CI run the secret scan.
  3. Render rebuilds the API image: multi-stage Docker build, -j2 and --param ggc-min-expand=20 --param ggc-min-heapsize=32768 to stay inside free-tier memory.
  4. Container start: docker-entrypoint.sh maps PORT into config.json, applies DATABASE_URL if given, runs bootstrap.py --no-seed (waits for DB, applies 45 migrations, loads reference data once), starts the hourly refresh loop in the background, and execs the server.
  5. Vercel builds frontend with npm ci and vite build, serves dist, rewrites unknown paths to index.html.
  6. Post-deploy settings on Render: CORS_ORIGINS, PUBLIC_APP_URL, WEBAUTHN_ORIGINS set to the Vercel URL.

11.6 Rollback strategy

14. End-to-end workflow walkthroughs

14.1 Passenger books a flight

  1. Passenger signs in and opens Book a flight. The app loads the board (GET /flights) and reference data.
  2. Chooses a flight and travellers (1 to 9). The UI calls POST /api/records/bookings with quote: true.
  3. The API validates the UUID and traveller list, takes a per-flight advisory lock, rejects departed, landed or cancelled flights (409), computes a distance-based fare in the origin's currency, applies a 10% Pro discount if an approved pass exists, and returns the quote.
  4. Passenger confirms; the same call without quote assigns seats under the lock, generates a PNR and a passenger reference (PAX- plus 6 hex), and stores the booking with status Confirmed and payment Unpaid.
  5. The UI refreshes My Trips.

14.2 Check-in to boarding with pre-checks

  1. The passenger (or a desk role) moves a traveller to Checked in. Every other stage is a desk step: only airport admins, ground staff and security can do it, otherwise 403.
  2. Stages advance exactly one step at a time (Booked, Checked in, Bag dropped, Security cleared, Boarded); skipping returns 409 Steps must be done in order.
  3. Ground staff records the id and bag checks (action: check). Without both, Bag dropped returns 409 Verify the ID and check the bag first.
  4. Security records screen or a hold note. Without a screen, Security cleared returns 409; while a hold note is set, any stage change returns 409 On hold.
  5. Boarded needs payment marked Paid (set by the airline or the airport desk), otherwise 409.
  6. Each update is written to the audit log; the director's board and the passenger's journey screen read the same booking record.

14.3 Passenger orders food, retailer fulfils

  1. Passenger opens Shops and Food, picks a shop and items (prices in the airport's local currency).
  2. The UI posts shopId and items (id, qty) to /api/records/orders. The server rejects closed shops (409), items not sold by that shop, unavailable items (409) and quantities outside 1 to 20.
  3. Totals come from stored prices, never from the client. Stock is decremented with a conditional UPDATE (stock >= qty); if it affects no row the order fails with 409 out of stock.
  4. The retailer's Orders tab shows orders for their shop only; they move it through Accepted, Preparing, Ready, Out for delivery, Delivered, or cancel.
  5. The passenger can cancel while the order is New; cancelling returns the stock. Orders and bookings are cancelled, not deleted, except by admins.

17. Interview prep: 30 questions with strong answers

Answers are in first person and specific to this repository. Where I describe a gap, it is a real gap from section 16.

Q1-Q8: Fundamentals

Q1: What is AeroBase India and what problem does it solve?

A: It is a multi-tenant airport-management SaaS. An airport is many organisations sharing gates, bags and security lanes, and they usually learn about a disruption through different tools at different times. I built one tenant-scoped data model and one live board, then gave each role its own workspace: director, ground staff, security, airline ops, pilots, retailers and passengers. The key point is that rules live on the server. For example a passenger cannot board until check-in, bag drop and screening are recorded, and the API returns 409 if someone skips a step. The reference dataset covers 20 airports, 958 routes and 74 airlines.

Follow-up: If a customer only wanted passenger features, what would you cut first?

Q2: Walk me through the stack end to end.

A: The frontend is React 19 with TypeScript, Vite and Tailwind, using TanStack Query for server state and Zustand for the session. It talks over HTTPS and JSON to a C++17 API built on Drogon, which uses libpqxx for PostgreSQL and hiredis for optional Redis. A small Flask service with a scikit-learn RandomForest predicts delays. In production the frontend is static on Vercel and the API, ML service, Postgres and Redis run from a Render Blueprint. Everything free-tier.

Follow-up: Where would the first failure occur at ten times the load?

Q3: How does authentication work?

A: Users sign in with email and password at /login. The API checks a login throttle, verifies a PBKDF2-HMAC-SHA256 hash at 600,000 iterations, and returns an HS256 JWT with user id, tenant id, role, airport and org claims. The token lives eight hours by default. The frontend stores it in a persisted Zustand store, adds it as a Bearer header through an Axios interceptor, and logs out on any 401. Passkeys through WebAuthn are a second path.

Follow-up: What is your answer to the token being in localStorage?

Q4: What does multi-tenancy mean here and how is it enforced?

A: Each airport is a tenant, a row in tenants. Almost every table carries tenant_id, and every query I wrote filters on the tenant claim from the JWT, not on anything the client sends. Only SUPER_ADMIN can look at another airport using the X-Tenant-ID header. It is logical isolation in a shared schema, which is cheap to run and easy to migrate.

Follow-up: How would you prove no query forgets the tenant filter?

Q5: Why a C++ backend?

A: I wanted small memory use and predictable latency on free tiers, and a single native binary that ships in one Docker image. Drogon gives me an async event loop, route auto-registration and filters. The cost is slow compiles and slower feature work than in Node or Go. On Render the build ran out of memory until I added -j2 and GCC memory parameters.

Follow-up: Would you pick C++ again for a team of five?

Q6: How are users separated by role?

A: Three layers. First a deny-by-default route guard classifies each path as Public, AnyUser or Admin before routing. Second, handlers check roles for sensitive actions, for example team management needs AIRPORT_ADMIN or SUPER_ADMIN. Third, the generic records engine has a policy per collection: who can read, create and modify, whether reads are limited to your own rows, and whether airline or shop roles are scoped to their organisation.

Follow-up: What happens if a developer adds a route and forgets the guard?

Q7: What is the fare model?

A: Fares are indicative. I compute great-circle distance between the two airports from reference_airports, apply low-cost-carrier per-kilometre rates in INR, give approved Pro pass holders 10% off, and convert to the airport's currency for overseas hubs. The server computes the price; the client price is never trusted. It is not a live airline feed and the README says so.

Follow-up: How would you plug in real fares?

Q8: What do the tests cover?

A: 63 integration tests run against a real API and Postgres: auth, role policies, booking quote and placement, stage gating, pre-checks, orders and stock. 76 Vitest tests cover pure logic like currency, booking and ops engines, plus some components. I also ran scripted Playwright sweeps per role to catch black screens and 403s. Honest gap: the unit and integration suites are not yet in GitHub Actions.

Follow-up: What is the first test you would add to CI?

Q9-Q15: Architecture and design

Q9: Describe the request lifecycle.

A: A Drogon pre-routing advice answers CORS preflights and calls routeguard::check. The guard classifies the path and, for protected ones, verifies the Bearer JWT with jwt-cpp, returning 401 or 403. Then the controller runs, reads claims, applies the policy, and runs parameterised SQL in a pqxx transaction on a per-thread connection. Post-handling advice adds CORS headers to every response.

Follow-up: Why do the checks happen before routing?

Q10: Why a generic JSONB records table?

A: Many small document types (bookings, passes, lost and found, orders, requests) across many roles would have needed dozens of tables and controllers. One app_records table with collection and data jsonb, indexed on tenant, collection and time, plus a policy per collection, let me add a collection with one policy entry. Where invariants matter I put dedicated handlers in front: bookings, orders, crew.

Follow-up: What do you lose compared with real tables?

Q11: How do you keep live data fresh?

A: The UI polls with TanStack Query: flights every 15 seconds and health every 10, paused in background tabs, with a slower probe when the backend is down. I chose polling because it is simple and robust on free hosting that sleeps. The API already has /ws/events and /ws/flights endpoints, but the main screens do not use them yet.

Follow-up: What would WebSockets change for scaling?

Q12: How is the booking engine designed?

A: placeBooking validates the flight id and 1 to 9 travellers, takes a per-flight Postgres advisory lock, rejects departed or cancelled flights, computes the quote, and when not in quote mode assigns seats, a PNR and a passenger reference in one transaction. Later changes go through updateBooking with actions cancel, stage, check and payment. Stages move one step at a time, and each gate returns 409 with a reason.

Follow-up: Why an advisory lock instead of a unique constraint?

Q13: How does the ML integration work and fail?

A: The API calls the Flask service with a 3 second timeout. The service loads a per-tenant model if one exists, otherwise a default model, otherwise uses a heuristic of weather times 1.5 plus congestion times 2. If the service is down the call returns failure and the API falls back. Tenant ids are validated by regex because they become part of a file name.

Follow-up: How would you evaluate the model's quality?

Q14: How do you deploy and bootstrap?

A: The Render Blueprint defines the API, ML, Postgres and Redis. The container entrypoint maps PORT into config, applies migrations through bootstrap.py, loads reference data once, optionally seeds demo data, starts an hourly refresh loop, then execs the server. The frontend is on Vercel with an SPA rewrite and security headers. I verified a cold start from an empty database and that a restart keeps data.

Follow-up: What is your rollback plan for a bad migration?

Q15: Why a hash-based router instead of React Router?

A: The shell has role-based navigation across about 128 pages, and I needed Back, Forward and refresh to work without nested routes. I synchronise the URL hash with the active page and an allow-list per role. It is small and works, though react-router-dom remains an unused dependency that I should remove.

Follow-up: What do you give up without a router?

Q16-Q21: Deep dives

Q16: Deep dive: what indexes exist and why?

A: The hot paths are the board and the records list. idx_flights_tenant_dep (tenant_id, departure_time) serves every board refresh, idx_records_lookup (tenant_id, collection, created_at DESC) serves every collection read, and a unique (tenant_id, flight_number, departure_time) makes seeding idempotent with ON CONFLICT. There are also unique constraints on seat per flight and gate code per tenant, a partial index on active partner keys, and indexes on billing and payment lookups.

Follow-up: How would you find slow queries in production?

Q17: Deep dive: how do you handle concurrency and double booking?

A: Seat assignment runs inside a transaction holding pg_advisory_xact_lock(hashtext(flightId)), so two bookings on the same flight serialise and capacity is checked on a consistent count. Orders use a conditional UPDATE on stock with stock >= qty; if no row is affected the order fails with 409. Booking updates read the row with FOR UPDATE.

Follow-up: What is the throughput ceiling of that lock?

Q18: Deep dive: performance and caching.

A: On the client I use lazy-loaded pages (49), TanStack Query stale-while-revalidate, a service worker for the shell and long immutable caching for hashed assets. On the server I keep one pqxx connection per IO thread, validated at most every 5 seconds, and Redis is optional. I have k6 and wrk scripts but have not recorded benchmark numbers, so I do not quote requests per second.

Follow-up: How would you load-test the booking path?

Q19: Deep dive: password and token security.

A: Passwords use PBKDF2-HMAC-SHA256 with 600,000 iterations and a random salt, stored as pbkdf2$iterations$salt$hash. Legacy unsalted SHA-256 hashes still verify so old accounts work. For unknown emails I verify against a dummy hash so timing does not leak existence. Login throttling allows five failures per ip and email, and thirty per ip, in fifteen minutes. JWTs are HS256 with a configurable TTL.

Follow-up: Why not argon2, and why not rotate the legacy hashes on login?

Q20: Deep dive: how would you scale this?

A: The API is stateless because of JWT, so I add replicas behind a load balancer. Per-thread DB connections mean connection count grows with threads times replicas, so PgBouncer comes next, then a read replica for analytics, then partitioning of app_records and flight_history. The in-process login throttle has to move to Redis first. The k8s manifests already include an HPA.

Follow-up: What breaks first on the database?

Q21: Deep dive: how is data recovered after a failure?

A: The migrations and bootstrap are idempotent, so an empty database rebuilds to a working demo state. Real data needs backups; there is a backup.sh script, and the free Render Postgres expires after 30 days, so for anything real I would use a permanent managed database with point-in-time recovery. Migrations are forward-only, so a bad one is fixed by a new migration.

Follow-up: What would a down-migration policy look like?

Q22-Q26: Trade-offs and why not X

Q22: Why not Node or Go for the API?

A: Either would have been faster to build. I chose C++ for footprint and learning value, accepting slower compiles and a smaller ecosystem. If this became a team product I would reconsider, because hiring and iteration speed matter more than saving memory.

Follow-up: What measurable benefit did C++ give you?

Q23: Why not WebSockets or SSE for everything?

A: Polling is simple, works through proxies, and survives a free-tier server that sleeps. It costs extra requests. The WebSocket endpoints exist, and I would switch the board and journey screens to them when concurrent users justify it.

Follow-up: How do you authenticate a WebSocket?

Q24: Why JWT instead of server sessions?

A: Stateless auth removes a session lookup and lets me run several replicas without shared session state. The cost is no server-side revocation and a secret whose rotation logs everyone out. A refresh-token model with short-lived access tokens, or httpOnly cookies, is my next step.

Follow-up: How would you revoke a stolen token today?

Q25: Why a JSONB store instead of strict tables?

A: Speed of delivery across many document types, with uniform tenant and role handling. The trade-off is weaker constraints and reporting, which I handle with dedicated handlers for the critical flows and indexed columns. There are also leftover relational tables (tickets, passenger_bookings) from an earlier design that I would consolidate.

Follow-up: Which collection would you move to real tables first?

Q26: Why free-tier hosting and what are its limits?

A: The goal was a live demo at zero cost. Render's free services sleep, so the first request takes about a minute, the free Postgres expires in 30 days, and builds are memory constrained. For production I would use an always-on instance and a permanent database.

Follow-up: What is the minimum paid setup you would recommend?

Q27-Q30: Behavioural, ownership and failure

Q27: Tell me about a hard production-style failure you fixed.

A: The Render build died at about 57 percent. I suspected out-of-memory on the free builder, since the C++ compile is heavy. I limited parallelism to -j2 and added GCC parameters to reduce peak memory, then kept a pre-built image as the fallback. I could only see a truncated log, so I treated it as a hypothesis and recorded the fallback.

Follow-up: How would you confirm the root cause?

Q28: Tell me about a bug you found through systematic testing.

A: During a sweep of every role I found the Accessibility page crashing on an undefined field, passengers getting 403 on lost-and-found, airline ops getting 403 on accessibility, and a false 'Sample data' banner on real pages. I fixed each at the right layer: null-safe code, widened policies where appropriate, a skip option on the collection hook, and a list of live pages. Then I re-ran the integration and unit suites.

Follow-up: How do you stop the same class of bug returning?

Q29: Tell me about a security mistake and how you handled it.

A: Credentials were exposed earlier (a Twilio token and a Google key appeared in chat and a screenshot). I added a secret scanner to CI and a pre-commit hook, documented a rotation runbook in docs/SECURITY.md, and flagged that only the key owner can rotate them. Rotation is still an open action item, and I say so.

Follow-up: What would you do about secrets already in git history?

Q30: How did you prioritise with limited time before a showcase?

A: I protected the demo path first: real flows over mock lists, role journeys without errors, a one-click deploy and a strong first impression on the landing page. Anything that could cause a black screen or a 403 in front of an audience went first. I also wrote down what is not finished, such as the unwired retention job and the CI gap, instead of hiding it.

Follow-up: What would you cut if you had half the time?
